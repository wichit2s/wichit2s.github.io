SLIDE 03 · TECHNICAL RISK ARCHITECTURE & DEPENDENCY SIGNALS
ROBERT C. MARTIN PRINCIPLES

แยก “ปัญหาทั่วไป” ออกจาก “ความเสี่ยงเชิงเทคนิค” เพื่อยกระดับโครงงาน

เกณฑ์ระดับพอใช้มักบันทึกแค่ “งานไม่ทัน” หรือ “เครื่องค้าง” แต่ระดับดีเยี่ยมต้องวิเคราะห์สาเหตุจากโครงสร้างโค้ด สถาปัตยกรรม และ Dependency

01 · FRAGILITY (ความเปราะบางของโค้ด) แก้ส่วนลดท้ายบิล แล้วภาษีมูลค่าเพิ่มพัง

เกิดขึ้นเมื่อโมดูลคำนวณราคา คูปอง และบัญชีสต็อกผูกติดกันแน่น (Tight Coupling) แก้จุดเดียวแต่กระทบหลายจุดที่ไม่มีความสัมพันธ์กันเชิงแนวคิด

การบรรเทา: แยก Policy/Strategy Pattern และเขียน Unit Test ครอบทุกกรณี
02 · VISCOSITY & WEEKLY BUILD PENALTY สภาพแวดล้อมหนืด จนทีมยอมเขียนโค้ดมักง่าย

หากการรัน Test หรือการ Merge โค้ดสัปดาห์ละครั้ง (Weekly Build) ใช้เวลานานและชนกันยับ นักศึกษาจะเลี่ยงการ Refactor และปล่อยหนี้ทางเทคนิคสะสม

การบรรเทา: ใช้ Continuous Integration (CI) และแบ่ง Component ย่อย
03 · STABLE-DEPENDENCIES PRINCIPLE (SDP) โมดูลแกนหลักห้ามพึ่งพาโมดูลที่เปลี่ยนบ่อย

โมดูล Core Ledger / Stock Transaction ที่ต้องเสถียร ห้ามไป Import โมดูล Promotion UI หรือ Third-party SDK ที่เปลี่ยนสเปกทุกสัปดาห์โดยตรง

การบรรเทา: กลับทิศทางการพึ่งพาด้วย Interface / Abstraction
04 · AI & SUPPLY CHAIN RISK ความเสี่ยงจากโค้ดและแพ็กเกจที่ AI แนะนำ

การใช้ AI ช่วยเขียนโค้ด POS อาจนำแพ็กเกจปลอม (Typosquatting), ไลบรารีล้าสมัย หรือตรรกะ Edge Case ที่ผิดพลาด เช่น ปัดเศษสตางค์ไม่ตรง

การบรรเทา: Strict Dependency Governance + Human PR Review

SLIDE 05 · PERFORMANCE BOTTLENECK ANATOMY IN GROCERY POS
TARGET SLA < 500 MS / CHECKOUT

4 คอขวดที่ทำให้ Grocery POS ค้างเมื่อลูกค้าต่อคิวพร้อมกันในชั่วโมงเร่งด่วน

ระบบที่ทดสอบบนเครื่องนักพัฒนาด้วยข้อมูล 50 ชิ้นจะไม่แสดงอาการ แต่เมื่อฐานข้อมูลมี 12,000 SKUs และเปิด 4 เครื่องพร้อมกัน คอขวดเหล่านี้จะปรากฏทันที

ลำดับ & จุดคอขวด อาการหน้างาน (Symptom) สาเหตุระดับโค้ดและฐานข้อมูล แนวทางแก้ไขเชิงวิศวกรรม
01
N+1 Query & Table Scan		 สแกนสินค้าชิ้นที่ 20 ในตะกร้าแล้วหน้าจอหน่วง 1.5–3 วินาที ลูปยิง Query หาส่วนลดและภาษีแยกทีละ SKU โดยไม่มี Composite Index บนคอลัมน์ barcode สร้าง Index บน barcode, ใช้ WHERE IN (...) แบบ Batch และ Cache กฎโปรโมชัน
02
Stock Lock Contention		 แคชเชียร์เครื่อง 2 กดชำระเงินแล้วหมุนค้าง Timeout Transaction เปิดค้างยาวเพื่อล็อกตารางสต็อกระหว่างรอสลิป/PromptPay ใช้ Optimistic Concurrency (version) หรือ Atomic UPDATE stock = stock - qty WHERE stock >= qty
03
Synchronous Blocking I/O		 กดปุ่มจ่ายเงินแล้วเครื่องค้างจนกว่าเครื่องพิมพ์หรือ API ธนาคารจะตอบ ประมวลผล Webhook, Email/LINE ใบเสร็จ และสร้าง PDF แบบ Blocking ใน Request หลัก ย้ายงานที่ไม่ใช่แกนหลักเข้า Background Queue (Async Worker) หลังยืนยัน Transaction
04
Heavy Payload & Re-render		 สลับหน้าจอบิลช้า กิน RAM บนแท็บเล็ตหรือเครื่อง POS สเปกต่ำ ดึงแค็ตตาล็อกทั้งหมด 12,000 แถวผ่าน JSON ทุกครั้งที่โหลดหน้า ทำ Pagination, Virtualized List และเก็บ Local Indexed/In-Memory Cache เฉพาะชุดสินค้าขายดี
MEASUREMENT RULE · AI SDLC GUIDE

ห้ามปรับจูนแบบเดาสุ่ม: ต้องวัดค่า Baseline ด้วย Load Test / Profiler ก่อนเปิดใช้งานการแก้ไขทุกครั้ง เพื่อให้พิสูจน์ได้ด้วยตัวเลขจริงว่า P95 Latency ลดลงกี่เปอร์เซ็นต์และไม่ทำให้ความถูกต้องของยอดเงินลดลง

SLIDE 08 · PDPA COMPLIANCE พ.ร.บ. คุ้มครองข้อมูลส่วนบุคคล พ.ศ. 2562
PRIVACY BY DESIGN

ข้อมูลบนเคาน์เตอร์ Grocery POS กับข้อกำหนด PDPA ที่ทีมพัฒนาห้ามมองข้าม

แม้จะเป็นร้านค้าปลีกทั่วไป แต่ทันทีที่ระบบ POS เก็บเบอร์โทรศัพท์สมาชิก เลขประจำตัวผู้เสียภาษี หรือประวัติการซื้อที่ระบุตัวตนได้ ระบบอยู่ภายใต้ขอบเขต PDPA ทันที

01 · LAWFUL BASIS & GRANULAR CONSENT แยกความยินยอม (ห้ามมัดรวม)

การเก็บข้อมูลเพื่อ ออกใบกำกับภาษี (Legal Obligation) หรือ สะสมแต้มสมาชิก (Contract) ต้องแยกจาก Checkbox ยินยอมส่งโปรโมชันการตลาด (Explicit Consent) และห้ามติ๊กเลือกไว้ล่วงหน้า

02 · DATA MINIMIZATION เก็บข้อมูลเท่าที่จำเป็นต่อวัตถุประสงค์

ลูกค้าที่จ่ายเงินสดและไม่เป็นสมาชิกไม่ควรถูกบังคับกรอกเบอร์โทรหรือเลขบัตรประชาชน เพื่อความสะดวกในการออกใบเสร็จย่อ

03 · SECURITY SAFEGUARDS & MASKING เข้ารหัสและพรางข้อมูลบนหน้าจอแคชเชียร์

เบอร์โทรศัพท์บนหน้าจอ POS และสลิปควรพรางเป็น 089-xxx-4321 เข้ารหัส PII ในฐานข้อมูล และส่งผ่าน HTTPS/TLS เสมอ

04 · RETENTION, RIGHTS & AUDIT TRAIL สิทธิเจ้าของข้อมูลและการลบทิ้งเมื่อพ้นกำหนด

รองรับคำขอเข้าถึง แก้ไข หรือลบ/ทำให้เป็นนิรนาม (Anonymize) ประวัติสมาชิก พร้อมบันทึก Log ว่าพนักงานคนใดเปิดดูข้อมูลลูกค้าเวลาใด

SLIDE 10 · SOFTWARE ETHICS FAIRNESS, ACCOUNTABILITY & AI GOVERNANCE
ENGINEERING PROFESSIONALISM

4 มิติจริยธรรมวิศวกรรมซอฟต์แวร์ในยุคระบบอัตโนมัติและ Agentic AI

ซอฟต์แวร์ที่ดีไม่ใช่แค่ทำงานเร็วและถูกกฎหมาย แต่ต้องไม่เอาเปรียบผู้บริโภค ไม่บิดเบือนความจริง และมีมนุษย์รับผิดชอบต่อโค้ดที่ส่งขึ้นระบบ

01 · NO DARK PATTERNS & PRICING FAIRNESS โปร่งใสต่อผู้ซื้อและแคชเชียร์

ห้ามออกแบบหน้าจอ POS หรือ Loyalty Portal ที่ซ่อนปุ่มยกเลิกสมาชิก ปัดเศษราคาขึ้นโดยไม่แจ้ง หรือแอบเปิดการเก็บข้อมูลโฆษณาเป็นค่าเริ่มต้น ความผิดพลาดของโปรโมชันต้องแสดงรายการชัดเจนบนใบเสร็จ

02 · HUMAN-IN-THE-LOOP FOR AGENTIC AI AI เขียนได้ แต่มนุษย์ต้องตรวจรับผิดชอบ

Google Cloud และคู่มือ Agentic AI ย้ำว่าโค้ดที่สร้างโดย AI ต้องผ่านการ Review จากสมาชิกในทีมแบบ Standard Pull Request ทุกครั้ง เพื่อป้องกันช่องโหว่ ตรรกะหลอน (Hallucination) และความเอนเอียง (Consensus/Coverage Bias)

03 · TRACEABILITY & ACCOUNTABILITY ไม่โยนความผิดให้ “บั๊ก” หรือ “AI”

เมื่อยอดเงินไม่ตรงหรือระบบตัดเงินซ้ำ ทีมพัฒนาต้องมี Audit Log ที่ตรวจสอบย้อนกลับได้จริง (Verification & Traceability) และรับผิดชอบแก้ไขเชิงระบบ แทนการแก้ตัวเลขในฐานข้อมูลแบบปกปิด

04 · SUSTAINABLE PACE & COLLECTIVE OWNERSHIP จริยธรรมต่อทีมพัฒนาด้วยกัน

Extreme Programming สอนเรื่อง Sustainable Pace และ Collective Code Ownership — การเร่งเขียนโค้ดข้ามคืนจนเปราะบางหรือหวงโค้ดไม่ให้เพื่อนตรวจ คือความเสี่ยงทางจริยธรรมที่ทำให้ทั้งทีมล้มเหลว
