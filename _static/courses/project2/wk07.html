SLIDE 04 • CLEAN CODE & SOLID PRINCIPLES

Don't Let the Sun Set on Bad Code: Refactoring ด้วย SOLID

Clean Architecture
SRP • SINGLE RESPONSIBILITY

1 คลาส 1 เหตุผลที่ต้องเปลี่ยน

แยก PriceCalculator (คำนวณราคารวม/ภาษี) ออกจาก InventoryRepository (คิวรีฐานข้อมูล) และ ReceiptFormatter

OCP • OPEN/CLOSED

ขยายได้โดยไม่แก้โค้ดเดิม

เพิ่มโปรโมชันสมาชิกหรือส่วนลดตามฤดูกาลผ่าน Strategy Interface โดยไม่ต้องแก้เงื่อนไข if-else ยาวในคลาสคิดเงิน

ISP & LSP • INTERFACE DISCIPLINE

แยกสิทธิ์และสัญญาให้ชัด

แคชเชียร์เรียกใช้เฉพาะเมธอดขายผ่าน IPosCheckout ไม่ถูกบังคับพึ่งเมธอดจัดการคลังของผู้ดูแลระบบ

DIP & DRY • DECOUPLING

พึ่ง Abstraction ไม่ผูก DB ตรง

Service ระดับสูงพึ่ง IStockStore ทำให้สลับ MySQL/PostgreSQL หรือใช้ Mock ทดสอบ Unit Test ได้ทันที 


          

        

      


      
      

        

          

            
SLIDE 05 • SPRINT 1 SECURITY & RELIABILITY

            
จุดเสี่ยงทางเทคนิค ของระบบ Grocery POS ใน Sprint 1

          

          

            Risk Mitigation
          

        


        

          

            
4 ข้อบังคับด้านความปลอดภัยและข้อมูล

            

              
                

                  หัวข้อ
                  ความเสี่ยงที่พบประจำ
                  วิธีป้องกันใน Sprint 1
                

              
              
                

                  Authentication
                  เก็บรหัสผ่าน Plaintext หรือส่ง password_hash กลับใน API
                  ใช้ bcrypt/argon2 และตัดฟิลด์ลับออกใน DTO response
                

                

                  Authorization
                  เช็กสิทธิ์แค่หน้า UI แต่ไม่ตรวจ role_enum บน API
                  บังคับ Role Middleware ทุก Endpoint (Cashier vs Manager)
                

                

                  SQL Injection
                  ต่อสตริง SQL ด้วย + เมื่อค้นหาบาร์โค้ดสินค้า
                  ใช้ Parameterized Query / ORM Prepared Statements เท่านั้น
                

                

                  Concurrency
                  ตัดสต็อกพร้อมกัน 2 เครื่องจนสินค้าเหลือติดลบ
                  ใช้ DB Transaction + Atomic Update (WHERE stock_qty >= qty)
                

              
            

          


          

            

              Serendipitous Decoupling (พลังของ Unit Testing):
              การเขียน Test ก่อนหรือเขียนคู่กับการพัฒนาโมดูล จะบังคับให้นักศึกษาแยกการคำนวณราคาและการตรวจสอบสต็อกออกจากฐานข้อมูลจริง ทำให้โครงสร้างโค้ดสะอาดขึ้นโดยอัตโนมัติ
            

            

              
ACCEPTANCE TEST RULE (XP)

              

                “เมื่อ Acceptance Test ของ User Story ใดผ่านแล้ว ให้บันทึกเป็นชุดทดสอบอัตโนมัติประจำระบบ และห้ามปล่อยให้พังซ้ำใน Commit ถัดไป”
              

            

            

              
EDGE CASES ที่ต้องมี TEST เสมอ

              
    
                
  • จำนวนสินค้าเป็น 0 หรือติดลบ (qty <= 0)
    • 
                
  • บาร์โค้ดซ้ำ / ไม่พบสินค้าในคลัง
    • 
                
  • การปัดเศษทศนิยมเงินตรา (หลีกเลี่ยง floating-point drift)
    •

เปลี่ยนคำแนะนำอาจารย์ที่ปรึกษา เป็น Actionable Backlog

          

          

            PDCA + QA Loop
          

        


        

          

            
1. MIRRORING & ACKNOWLEDGING

            

              ทวนความเข้าใจข้อเสนอแนะของอาจารย์ด้วยคำพูดของทีม (หลักการสัมภาษณ์ AUN-QA) เพื่อยืนยันว่าเข้าใจปัญหาตรงกันก่อนแก้ไข

              แตกความเห็นเป็น Issue พร้อมติด Label (advisor-feedback, refactor, bug) และกำหนด Assignee

              ปิดงานด้วยหลักฐานจริง: ลิงก์ PR ที่แก้แล้ว ผลการรัน Test และเดโมในคาบถัดไป (ตอบโจทย์ PDCA Check → Act)
