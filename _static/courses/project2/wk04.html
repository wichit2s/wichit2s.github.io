ค่านิยมหลัก 4 ประการสำหรับการทำงานโครงงาน

  • 1. บุคคลและการมีปฏิสัมพันธ์ เหนือกว่า กระบวนการและเครื่องมือ

SLIDE 04 / 10 FRAMEWORK COMPARISON · SCRUM & KANBAN

Scrum vs. Kanban — เลือกจังหวะและการไหลของงานให้เหมาะกับโครงงาน

ทั้ง Scrum และ Kanban ต่างมีเป้าหมายเพื่อส่งมอบงานให้เร็วและมองเห็นปัญหาได้ไว แต่มีจังหวะการวางแผนและการคุมปริมาณงานต่างกัน สำหรับโครงงานนักศึกษา 3–5 คน แนวทางผสม (Scrumban) มักได้ผลดีที่สุด

มิติการเปรียบเทียบ Scrum (เน้นรอบ Sprint คงที่) Kanban (เน้นการไหลต่อเนื่อง) การประยุกต์ใช้ใน 1145 204
รูปแบบการทำงาน แบ่งเป็นรอบเวลาคงที่ 1–4 สัปดาห์ (Time-boxed Sprints) ไหลต่อเนื่องตลอดเวลา ไม่รอจบรอบ Sprint วางแผน Sprint ละ 2 สัปดาห์ตามปฏิทินตรวจงาน
การควบคุมปริมาณงาน กำหนด Sprint Commitment ตาม Capacity ของทีม ใช้ WIP Limits จำกัดจำนวนงานที่กำลังทำพร้อมกัน จำกัดช่อง In Progress ไม่เกิน 1 งานต่อ 1–2 คน
บทบาทหน้าที่ Product Owner, Scrum Master, Developers ไม่มีบทบาทบังคับตายตัว เน้นความรับผิดชอบร่วมกัน หมุนเวียนคนดูแลบอร์ด (Scrum Master) ในแต่ละ Sprint
การปรับเปลี่ยนระหว่างทาง ไม่เปลี่ยนขอบเขตกลาง Sprint หากไม่กระทบเป้าหมายหลัก ปรับลำดับคิวงานได้ทันทีเมื่อมีงานแทรกด่วน งาน Bug ด่วนระหว่างทดสอบเข้าช่อง Kanban ได้เลย
ตัวชี้วัดหลัก (Metrics) Velocity, Burndown / Burn-up Chart Lead Time, Cycle Time, Cumulative Flow Diagram ใช้ Burn-up ของ GitHub Projects / Jira ติดตามงาน

SLIDE 07 / 10 PULL REQUEST WORKFLOW & QUALITY GATES

Pull Request Workflow: ด่านคัดกรองคุณภาพก่อนโค้ดเข้าสู่สาขาหลัก

Pull Request (PR) ไม่ใช่แค่ปุ่มกดรวมโค้ด แต่เป็นกระบวนการสื่อสารทางเทคนิค (Peer Review) และด่านตรวจสอบอัตโนมัติ (CI Pipeline) เพื่อให้มั่นใจว่าโค้ดใหม่ไม่ทำลายฟีเจอร์เดิมของเพื่อนในทีม

STEP 01–02

เปิด PR พร้อม Template และ Link Issue

ใช้ไฟล์ .github/PULL_REQUEST_TEMPLATE/feature_pr_template.md บังคับกรอก: คำอธิบายฟีเจอร์, ผลลัพธ์ที่คาดหวัง, รายการ Test Cases (- [ ]) และเชื่อม Issue ด้วยคำสั่ง Closes #15 แล้วลากการ์ดไปคอลัมน์ Awaiting Review

STEP 03–04

ด่านตรวจอัตโนมัติ (CI Pipeline)

ทุกครั้งที่ Push โค้ดขึ้น PR ระบบ CI (เช่น GitHub Actions) จะรัน: Source Control → Build → Automated Unit/Integration Tests → Static Code Analysis (Linter / Security Scan) หากไม่ผ่าน ห้ามกด Merge เด็ดขาด

STEP 05–06

Peer Review & Auto-Merge

กำหนด Reviewers อย่างน้อย 1–2 คนตรวจ Logic และ Edge Cases เมื่อ Approve และ CI ขึ้นสีเขียวครบจึง Squash/Merge เข้า develop จากนั้นบอทจะย้ายการ์ดไป Done และปิด Issue ให้อัตโนมัติ

AI IN PR WORKFLOW

ใช้ AI ช่วยเขียนและตรวจโค้ดอย่างมีวินัย

เครื่องมือ Agentic AI และ Copilot สามารถช่วยร่าง Unit/Regression Test, สรุปคำอธิบาย PR และสแกนช่องโหว่ Dependency ได้ แต่ Human-in-the-Loop เป็นสิ่งบังคับ: นักศึกษาต้องอ่าน เข้าใจ และตรวจสอบหลักฐานการรัน Test จริงก่อนกด Approve เสมอ
