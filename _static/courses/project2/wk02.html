SLIDE 03 · PROBLEM DISCOVERY หัวข้อที่ 1: การสำรวจและวิเคราะห์โจทย์ปัญหาด้าน Data Science & Software Innovation

แยก "อาการของปัญหา" ออกจาก "รากปัญหาที่แก้ได้ด้วยระบบ"

โจทย์ที่ดีต้องไม่ได้เริ่มจาก "อยากใช้เทคโนโลยีอะไร" แต่เริ่มจาก "ใครกำลังประสบปัญหาอะไร ข้อมูลใดมีอยู่จริง และวัดผลดีขึ้นได้อย่างไร"

STEP 01

Pain Point จริง

ระบุขั้นตอนที่ช้า ผิดพลาดซ้ำ หรือสูญเสียต้นทุนในธุรกิจ/หน่วยงาน (เช่น สต็อกขาด หรือคีย์ข้อมูลซ้ำซ้อน)

STEP 02

ผู้ได้รับผลกระทบ

ใครคือผู้ใช้หลัก (เช่น แคชเชียร์ เจ้าของร้าน ผู้จัดการคลัง) และมีความถี่ในการใช้งานบ่อยเพียงใด

STEP 03

ความพร้อมของข้อมูล

มีข้อมูล Transaction, CSV หรือ Logs ให้ทดสอบหรือไม่ หากต้องเก็บใหม่ต้องไม่ติดข้อจำกัด PDPA

STEP 04

คุณค่าที่วัดผลได้

ระบุผลลัพธ์เชิงปริมาณก่อน-หลัง (เช่น ลดเวลาเช็กสต็อก, แจ้งเตือนก่อนสินค้าหมดล่วงหน้า)

มิติการวิเคราะห์ โจทย์สาย Software Innovation (SI) โจทย์สาย Data Science (DS)
จุดเน้นของปัญหา กระบวนการทำงานติดขัด ขาดระบบรวมศูนย์ การทำงานซ้ำซ้อน หรือข้อมูลไม่ซิงค์กัน มีข้อมูลจำนวนมากแต่ขาดการวิเคราะห์เชิงลึก ไม่รู้แนวโน้มหรือจุดตัดสินใจที่แม่นยำ
แนวทางแก้ปัญหา (Solution) ออกแบบ Web/App Workflow, Relational DB (3NF), API, ระบบสิทธิ์ และ Automated Testing Data Pipeline ทำความสะอาดข้อมูล, Exploratory Analytics, โมเดลพยากรณ์/แนะนำ, Dashboard
หลักฐานความสำเร็จ Working Software ที่ทำงานครบ User Stories, API ถูกต้อง, ผ่าน Unit/Integration & Usability Test Data Insights ที่นำไปตัดสินใจได้จริง, Dashboard ชัดเจน, ค่าชี้วัดโมเดล (เช่น MAE, Precision)
สูตร "Elevator Test Statement" สำหรับสรุปโจทย์ปัญหาให้คมชัดใน 3 ประโยค:

"สำหรับ [กลุ่มผู้ใช้งานเป้าหมาย] ที่ประสบปัญหา [Pain Point หลัก], ระบบ [ชื่อโครงงาน] เป็น [ประเภทซอฟต์แวร์/Data Product] ที่ช่วยให้ [ประโยชน์สำคัญที่วัดได้] แตกต่างจากวิธีเดิมตรงที่ [จุดเด่นของแนวทางใหม่]"

SLIDE 04 · SMART OBJECTIVES หัวข้อที่ 2: การกำหนดวัตถุประสงค์และขอบเขตโครงงานที่วัดผลได้

เปลี่ยนเป้าหมายกว้าง ๆ ให้เป็นวัตถุประสงค์แบบ SMART

ตามกรอบประกันคุณภาพ AUN-QA วัตถุประสงค์ที่ดีต้องสังเกตและประเมินได้ชัดเจน เพื่อใช้ตรวจรับงานในวันสอบ Midterm และ Final Defense

S · Specific

จำเพาะเจาะจง

ระบุชัดว่าพัฒนาระบบอะไร สำหรับผู้ใช้กลุ่มใด ครอบคลุมโมดูลใดบ้าง

M · Measurable

วัดผลได้

มีตัวเลขหรือเกณฑ์ชี้วัด เช่น จำนวน Test Cases, Test Coverage, เวลาตอบสนอง หรือค่าความแม่นยำ

A · Achievable

ทำได้จริง

สอดคล้องกับทักษะและจำนวนสมาชิก (1–3 คน) ไม่ต้องพึ่งทรัพยากรที่เข้าไม่ถึง

R · Relevant

ตรงประเด็น

แก้ Pain Point ใน Problem Statement และตอบโจทย์สาย DS/SI ของรายวิชา

T · Time-bound

มีกรอบเวลาชัด

แบ่งส่งมอบเป็น Milestone ได้ภายใน 15 สัปดาห์ (MVP สัปดาห์ 8, Final สัปดาห์ 15)

ตัวอย่างที่ควรหลีกเลี่ยง (คลุมเครือ)
  • "เพื่อพัฒนาระบบร้านค้าออนไลน์ให้ทันสมัยและใช้งานง่าย" (วัดผลไม่ได้ ไม่ระบุโมดูลและผู้ใช้)
  • "เพื่อใช้ AI ทำนายยอดขายให้แม่นยำที่สุดเท่าที่จะทำได้" (ไม่มีเกณฑ์ชี้วัด ไม่มีกรอบข้อมูลและเวลา)
  • "เพื่อสร้างแพลตฟอร์มระดับองค์กรรองรับทุกสาขาทั่วประเทศ" (ใหญ่เกินกำลังคนปี 2 ใน 15 สัปดาห์)
ตัวอย่างที่ดีตามหลัก SMART (วัดผลได้)
  • "พัฒนาระบบ POS หน้าร้านและตัดสต็อกคลังสินค้าแบบ 3NF สำหรับร้านขายของชำ 1 สาขา พร้อมแจ้งเตือนสินค้าใกล้หมดภายใน 15 สัปดาห์"
  • "สร้างโมเดลคำนวณ Reorder Point และ Dashboard สรุปสินค้าขายดี/ชั่วโมงเร่งด่วน โดยผ่านการทดสอบ Usability จากผู้ใช้จริงอย่างน้อย 5 ราย"

SLIDE 07 · CASE STUDY หัวข้อที่ 3: กรณีศึกษาตัวอย่างระบบ Grocery POS Platform

Grocery POS Platform: จากปัญหาหน้าร้านค้าปลีกสู่ขอบเขตโครงงานปี 2

ประยุกต์โครงสร้างระบบ POS ร้านค้าสู่บริบทร้านขายของชำ/ซูเปอร์มาร์เก็ตขนาดเล็ก (Grocery) ที่มีสินค้าหลากหลาย SKU และวันหมดอายุ

Problem Statement ตัวอย่าง (Grocery Store):

ร้านขายของชำท้องถิ่นมีสินค้ากว่า 800–1,500 SKU แต่ยังจดบันทึกยอดขายด้วยกระดาษหรือสเปรดชีต ทำให้เกิดปัญหาคิดเงินช้าในช่วงเร่งด่วน สต็อกสินค้าหมดโดยไม่รู้ตัว สินค้ากลุ่มนม/เบเกอรีหมดอายุค้างสต็อก และเจ้าของร้านไม่มีข้อมูลประกอบการสั่งซื้อสินค้าเข้าคลังอย่างมีระบบ

In-Scope (ทำจริงใน 15 สัปดาห์ · ปี 2 Practiced)
  • POS Checkout: ค้นหา/สแกนรหัสสินค้า คำนวณยอดรวม รับเงินสด/PromptPay QR และออกใบเสร็จ
  • Batch & Expiry Inventory: ตัดสต็อกอัตโนมัติตามล็อตสินค้า พร้อมแจ้งเตือนสินค้าต่ำกว่า Reorder Point และใกล้หมดอายุ
  • Sales & Reorder Analytics: คำนวณจุดสั่งซื้อใหม่ (ROP) แสดงสินค้าขายดี และช่วงเวลาเร่งด่วน (Peak Hours)
  • QA & Deployment: ทดสอบ Unit/Integration Test และติดตั้ง Live Web App สำหรับ 1 สาขา
Out-of-Scope (ตัดออก เพื่อต่อยอดปี 3 Mastery)
  • Multi-Branch Cloud Microservices: สถาปัตยกรรม Kubernetes แยกหลาย Service รองรับหลายสิบสาขาพร้อมกัน
  • Offline-First Hardware Sync: ระบบแคช Local IndexedDB และเชื่อมต่อเครื่อง EDC/ลิ้นชักเก็บเงินจริง
  • Deep Learning Forecasting: โมเดล LSTM พยากรณ์ร่วมกับข้อมูลสภาพอากาศและจราจรหลายปี
  • ระบบบัญชีภาษีเต็มรูปแบบ: การออกใบกำกับภาษีอิเล็กทรอนิกส์ (e-Tax) และเชื่อมกรมสรรพากร
Core Relational Tables (Normalized to 3NF)

• Users (user_id, username, password_hash, role_enum)
• Categories (category_id, category_name, shelf_zone)
• Products (product_id, category_id, barcode, sku_name, unit_price, reorder_point)
• Inventory_Batches (batch_id, product_id, qty_remaining, cost_per_unit, expiry_date)
• Orders (order_id, user_id, order_datetime, total_amount, payment_method, status)
• Order_Items (order_item_id, order_id, batch_id, quantity, subtotal)
จุดสังเกตด้านวิศวกรรมข้อมูล (ปี 2)

ความแตกต่างสำคัญระหว่างร้านกาแฟกับ Grocery POS คือการเพิ่มตาราง Inventory_Batches เพื่อติดตามวันหมดอายุ (FEFO: First-Expired, First-Out) และ barcode สำหรับค้นหาสินค้าความเร็วสูงหน้าร้าน

ความเสี่ยงทางเทคนิคที่ต้องวางแผน (CLO3): กรณีสินค้า 1 ชิ้นถูกตัดสต็อกพร้อมกันจาก 2 หน้าจอ (Concurrency / Race Condition) ต้องใช้ Database Transaction เพื่อรักษาความถูกต้องของยอดคงเหลือ

ตัวอย่าง Agile User Stories
  • Cashier: "ในฐานะพนักงานแคชเชียร์ ฉันต้องการสแกนบาร์โค้ดสินค้าและเลือกวิธีชำระเงิน เพื่อคิดเงินและออกใบเสร็จให้ลูกค้าได้ภายใน 30 วินาที"
  • Store Manager: "ในฐานะผู้จัดการร้าน ฉันต้องการดูรายการสินค้าที่ต่ำกว่า Reorder Point และใกล้หมดอายุใน 7 วัน เพื่อวางแผนสั่งซื้อและจัดโปรโมชันลดราคาได้ทันเวลา"
  • Analyst / Owner: "ในฐานะเจ้าของร้าน ฉันต้องการดูรายงานยอดขายแยกตามหมวดหมู่และช่วงเวลา Peak Hours เพื่อจัดตารางพนักงานและสต็อกสินค้าให้เหมาะสม"
จริยธรรมและความเป็นส่วนตัวข้อมูล (PLO5 / PDPA)

ในการเก็บข้อมูลการขายหรือประวัติสมาชิก (Loyalty) เพื่อนำไปวิเคราะห์หรือทดสอบระบบ:

  • ไม่เก็บข้อมูลส่วนบุคคลที่ไม่จำเป็น (Data Minimization) เช่น เลขบัตรประชาชน
  • ทำการ Mask / Anonymize เบอร์โทรศัพท์หรือรหัสสมาชิกก่อนนำข้อมูลไปวิเคราะห์บน Dashboard
  • ใช้ password_hash สำหรับบัญชีผู้ใช้และแยกสิทธิ์ Admin กับ Cashier ชัดเจน

  • ฟีเจอร์เด่น: ระบบตะกร้าแบบ Hotkey/Barcode, คืนสินค้า/ยกเลิกบิล, แจ้งเตือนสต็อกและวันหมดอายุอัตโนมัติ
