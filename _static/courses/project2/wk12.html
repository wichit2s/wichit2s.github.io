SLIDE 03 / 12 TESTING STRATEGY & PYRAMID

พีระมิดการทดสอบซอฟต์แวร์ (The Testing Pyramid)

ทีมวิศวกรรมซอฟต์แวร์ไม่ควรพึ่งการคลิกทดสอบด้วยมือทั้งหมด (Ice-Cream Cone Anti-pattern) เพราะช้าและเกิดช่องว่างของ Regression Suite มากขึ้นเรื่อยๆ ตามจำนวนฟีเจอร์ ลองปรับสัดส่วนชุดทดสอบด้านขวาเพื่อเปรียบเทียบผลลัพธ์

UNIT TESTS (ฐาน 60–70%)
ทดสอบฟังก์ชันคำนวณราคา ส่วนลด เงินทอน ในระดับมิลลิวินาทีด้วย In-Memory / Mock

ทดสอบ API เชื่อม DB จริง การตัดสต็อก Transaction และการเตือน Reorder
E2E / USABILITY (ยอด 10%)
ทดสอบ flow ขายหน้าร้านครบวงจร และ Usability Testing กับผู้ใช้เป้าหมาย

SLIDE 04 / 12 UNIT TESTING • TDD • MOCK OBJECTS

Unit Testing & Test Isolation ด้วย Mock / In-Memory Gateway

อ้างอิงแนวคิดจาก Robert C. Martin: การเขียน Unit Test ก่อนหรือคู่กับโค้ด (Red → Green → Refactor) บังคับให้เราแยก Business Logic ออกจากฐานข้อมูลจริงได้ ด้วยการใช้ Mock Object หรือ InMemoryProductGateway ทำให้ทดสอบระบบ POS ได้รวดเร็วโดยไม่ต้องรอต่อ Database ทุกครั้ง

กฎ 3 ข้อของ TDD
  1. ห้ามเขียน Production Code จนกว่าจะมี Unit Test ที่ Fail (Red)
  2. เขียน Test เท่าที่จำเป็น ให้พอล้มเหลวหรือคอมไพล์ไม่ผ่าน
  3. เขียน Production Code เท่าที่จำเป็น เพื่อทำให้ Test ผ่าน (Green) แล้วจึง Refactor
// ตัวอย่างโครงสร้าง Unit Test (Isolated Order Logic)
function calculateLineSubtotal(price, qty, discountPct = 0) {
  if (qty <= 0) throw new Error('Invalid quantity');
  const raw = price * qty * (1 - discountPct / 100);
  return Math.round(raw * 100) / 100;
}

// ใช้ InMemoryInventory แทน Real SQL DB เพื่อความเร็ว
test('TC-U01: คำนวณราคาน้ำมันพืช 2 ขวด ลด 10%', () => {
  expect(calculateLineSubtotal(55, 2, 10)).toBe(99.00);
});

SLIDE 05 / 12 INTEGRATION TESTING • DATABASE TRANSACTIONS

Integration Testing และการป้องกันสต็อกตัดขนานพร้อมกัน

Unit Test ยืนยันว่าฟังก์ชันย่อยถูกต้อง แต่ไม่สามารถจับปัญหาเมื่อ UI, API, Payment และ Database ทำงานร่วมกัน โดยเฉพาะความเสี่ยงสำคัญในเอกสารโครงงาน: ปัญหาสต็อกตัดขนานพร้อมกันเมื่อแคชเชียร์หลายจุดสั่งซื้อสินค้าชิ้นสุดท้ายพร้อมกัน (Race Condition)

CONCURRENT POS INTEGRATION SIMULATOR

ขอบเขตของ Integration Test ใน Grocery POS

  • API + Database: สร้าง Orders และ Order_Items พร้อมตัด Inventory.stock_quantity ใน Transaction เดียว (ถ้าขั้นตอนใดพังต้อง Rollback ทั้งหมด)
  • Payment Webhook: จำลอง PromptPay QR สำเร็จ / หมดเวลา (Timeout) / ยิงซ้ำ (Idempotency) เพื่อไม่ให้สร้างใบเสร็จซ้ำ
  • Low-Stock Alert Trigger: ตรวจสอบว่าการขายที่ทำให้ stock_quantity <= reorder_level สร้างการแจ้งเตือนทันที

SLIDE 07 / 12 ACCEPTANCE TESTING (ATDD) • PDPA ETHICS

Acceptance Testing และการตรวจสอบจริยธรรมข้อมูล (PDPA)

Acceptance Test คือ “ข้อตกลงที่รันตรวจสอบได้” ร่วมกับลูกค้า (Black-box) โดยเขียนด้วยภาษาธุรกิจ (Given-When-Then) พร้อมทั้งต้องตรวจการคุ้มครองข้อมูลส่วนบุคคล (PDPA) ตามข้อกำหนดรายวิชา เช่น การไม่เปิดเผยเบอร์โทร เลขบัตรประชาชน หรือ password_hash ในรายงานและชุดทดสอบ

# Bug Fix Title: [BUG-104] ป้องกันสต็อกติดลบเมื่อขายพร้อมกัน

### Issue Description
เครื่อง POS 2 จุดสแกนสินค้าชิ้นสุดท้ายพร้อมกัน ทำให้ stock_quantity กลายเป็น -1

### Steps to Reproduce
1. ตั้งค่าสินค้า SKU-008 ให้ stock_quantity = 1
2. กด Confirm Order จาก POS-01 และ POS-02 พร้อมกัน

### Expected Behavior

          SLIDE 12 / 12
          KEY TAKEAWAYS & REFERENCES
        


        

          สรุปประเด็นสำคัญ สัปดาห์ที่ 12 และแหล่งอ้างอิงรายวิชา
        

        

          คุณภาพของแพลตฟอร์ม Grocery POS ไม่ได้เกิดจากการ “ตรวจตอนจบ” แต่เกิดจากการออกแบบระบบให้ทดสอบได้ (Testability) ตั้งแต่วันแรก และยืนยันผลทั้งด้วยชุดทดสอบอัตโนมัติและผู้ใช้จริงหน้าร้าน
        


        

          

            TAKEAWAY 01 • CODE & ISOLATION
            
Unit Test ช่วยแยก Business Logic ให้สะอาด

            
การใช้ In-Memory Gateway / Mock Object ทำให้ทดสอบกฎการคิดเงินและสต็อกได้ในเสี้ยววินาทีและลดความเปราะบางของโค้ด

          

          

            TAKEAWAY 02 • TRANSACTIONS
            
Integration Test ป้องกันความล้มเหลวรอยต่อระบบ

            
ปัญหาสต็อกตัดขนานพร้อมกัน (Concurrency) และ PromptPay Webhook ซ้ำซ้อน ต้องถูกดักจับด้วย Integration Test บน Database จริง

          

          

            TAKEAWAY 03 • HUMAN-CENTERED QA
            
Usability Testing คือบทพิสูจน์หน้าเคาน์เตอร์

            
ให้แคชเชียร์และเจ้าของร้านจริงทำภารกิจสำคัญ สังเกตจุดติดขัดโดยไม่ชี้นำ แล้วแปลงปัญหาเป็นรายการแก้ไขที่วัดผลได้

          

          

            TAKEAWAY 04 • MEASURABLE OUTCOMES
            
วัดผลด้วย Metrics และคุ้มครอง PDPA

            
ติดตาม Pass Rate, Escaped Defects, Lead Time และตรวจความถูกต้องของ Test ที่สร้างจาก AI พร้อมลบข้อมูลส่วนบุคคลออกจาก Test Dataset เสมอ
