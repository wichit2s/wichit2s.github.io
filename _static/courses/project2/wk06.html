SLIDE 02 · BACKLOG GROOMING Walking Skeleton & MoSCoW

Backlog Grooming: คัดงานที่สร้างคุณค่าแรกด้วย Walking Skeleton

Product Backlog ไม่ใช่รายการสิ่งที่ต้องทำทั้งหมดในคราวเดียว การทำ Refinement (Grooming) คือการเรียงลำดับความสำคัญด้วยโมเดล MoSCoW (Must, Should, Could, Won't) และเลือกชุดงานขั้นต่ำที่เชื่อมต่อระบบตั้งแต่ฐานข้อมูลถึงหน้าจอได้จริง (Walking Skeleton) เพื่อเข้าสู่ Sprint 1

ข้อควรระวังในการเขียน User Story: รูปแบบมาตรฐานต้องระบุ As a [บทบาท], I want to [สิ่งที่ต้องการ] so that [คุณค่าที่ได้] และต้องมี Acceptance Criteria แบบ Given–When–Then ที่ทดสอบได้จริง มิฉะนั้นคะแนนประเมินหมวด Requirements & Backlog จะตกอยู่ในระดับพอใช้ (14–17 คะแนน)
SLIDE 03 · ESTIMATION Story Points & Planning Poker

Story Points วัดขนาดและความเสี่ยงสัมพัทธ์ ไม่ใช่จำนวนชั่วโมง

ตามหลักของ Mike Cohn นักพัฒนามักประเมินเวลาเป็นชั่วโมงพลาดเมื่อเจอความไม่แน่นอน การใช้ Story Points แบบลำดับฟีโบนัชชี (1, 2, 3, 5, 8, 13) ช่วยให้ทีมเปรียบเทียบขนาดสัมพัทธ์ได้รวดเร็ว เช่น งาน 8 คะแนนใช้แรงและความซับซ้อนประมาณสองเท่าของงาน 4 คะแนน และหากงานใดเกิน 8 คะแนนต้องแบ่ง (Split) ให้เล็กลงก่อนนำเข้า Sprint

SLIDE 05 · DOCKER ENVIRONMENT Eliminate Environment Viscosity

Docker Environment: จบปัญหา "เครื่องฉันรันได้" ด้วย Container เดียวกัน

เมื่อทีมมีสมาชิกหลายคนที่ใช้ Windows, macOS หรือ Linux ต่างกัน ความหนืดของสภาพแวดล้อม (Viscosity) จะทำให้เสียเวลากับเวอร์ชัน Database หรือ Runtime ไม่ตรงกัน Docker Compose ช่วยให้ทั้ง Frontend, Backend API และ PostgreSQL ทำงานด้วยคำสั่งเดียวและตั้งค่าผ่าน .env อย่างปลอดภัย

            SLIDE 06 · WORKFLOW & CI GATE

GitHub Projects & CI: ทำงานเป็นทีมเหมือนทีม Pit Crew Formula 1

        


        

          Continuous Integration (CI) ป้องกันอาการ "Morning-After Syndrome" ที่โค้ดพังเมื่อรวมงานปลายสัปดาห์ ทุก Task ใน Sprint 1 ต้องเชื่อมกับ GitHub Issue ผ่าน Branch ย่อยและ Pull Request พร้อมผ่านด่าน Automated Test ก่อนย้ายการ์ดไป Done

            SLIDE 08 · DOD, RISKS & RUBRIC
            Quality & 25-Point Evaluation
          

          
Definition of Done, แผนลดความเสี่ยง และเกณฑ์ประเมิน 25 คะแนน

        


        

          งานที่ยังเขียนไม่เสร็จหรือยังไม่มี Automated Test จะไม่ถูกนับเป็น Increment ในวัน Sprint Review ทีมต้องกำหนด Definition of Done (DoD) ที่ชัดเจน ระบุความเสี่ยงทางเทคนิคตั้งแต่ต้น และตรวจสอบคุณภาพ Backlog ให้ตรงตามรูบริกของรายวิชา
        


        

          

            DEFINITION OF DONE (SPRINT 1: DATABASE & AUTH)
            
    
              
  • 1. Code & PR: โค้ดถูก Merge ผ่าน Pull Request และมีเพื่อนร่วมทีม Review อย่างน้อย 1 คน
    • 
              
  • 2. Tests Pass: Unit Test และ Acceptance Criteria (Given–When–Then) ผ่านครบ 100%
    • 
              
  • 3. Clean Build: รัน docker compose up --build บนเครื่องสมาชิกอื่นแล้วใช้งานได้ทันที
    • 
              
  • 4. Security & PDPA: ไม่มีรหัสผ่านแบบ Plain-text, ไม่ Commit .env, และไม่เก็บ PII เกินความจำเป็น
    •
