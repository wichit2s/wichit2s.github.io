03 · FR VS NFR FUNCTIONAL & NON-FUNCTIONAL REQUIREMENTS
INTERACTIVE CLASSIFIER

ความต้องการเชิงหน้าที่ (FR) เทียบกับความต้องการเชิงคุณภาพ (NFR)

FR ตอบคำถามว่า "ระบบต้องทำอะไรได้บ้าง" ส่วน NFR กำหนดว่า "ระบบต้องทำงานได้ดี ปลอดภัย และเสถียรแค่ไหน"

FUNCTIONAL REQUIREMENTS (FR)

สิ่งที่ระบบต้องดำเนินการ (Behavior)

  • FR-01 การสแกนและค้นหาสินค้า: ระบบอ่านบาร์โค้ด EAN-13 หรือค้นหาชื่อสินค้าเพื่อเพิ่มลงตะกร้า
  • FR-02 การคำนวณและชำระเงิน: คำนวณส่วนลด ภาษีมูลค่าเพิ่ม และออกใบเสร็จพร้อมบันทึกช่องทางชำระเงิน
  • FR-03 การตัดสต็อกอัตโนมัติ: ลดจำนวนสินค้าคงคลังทันทีเมื่อยืนยันการชำระเงิน และแจ้งเตือนเมื่อต่ำกว่าจุดสั่งซื้อซ้ำ
  • FR-04 การจัดการสิทธิ์ผู้ใช้: แยกสิทธิ์ Cashier กับ Manager ในการยกเลิกบิล (Void) หรือแก้ไขราคา
NON-FUNCTIONAL REQUIREMENTS (NFR)

คุณลักษณะเชิงระบบที่วัดผลเป็นตัวเลขได้

  • NFR-01 Performance: การค้นหาบาร์โค้ดและเพิ่มสินค้าลงตะกร้าต้องตอบสนองภายในไม่เกิน 300 มิลลิวินาที
  • NFR-02 Data Integrity: การตัดสต็อกหลายจุดพร้อมกันต้องเป็น Atomic Transaction ไม่มีสต็อกติดลบ
  • NFR-03 Security & PDPA: รหัสผ่านต้องเข้ารหัส Hash (bcrypt/Argon2) และปิดบังข้อมูลส่วนบุคคลลูกค้าในรายงานสรุป
  • NFR-04 Reliability: ระบบต้องทำงานออฟไลน์ชั่วคราวหรือกู้คืนบิลล่าสุดได้เมื่ออินเทอร์เน็ตสะดุด
CHECKPOINT · ฝึกแยกแยะ FR กับ NFR (บันทึกคำตอบอัตโนมัติ)

ลองคลิกจำแนกข้อกำหนดของ Grocery POS ต่อไปนี้

04 · SRS BLUEPRINT IEEE 830 / ISO 29148 ADAPTED FOR AGILE SOPHOMORE PROJECT
คลิกเพื่อเปิดดูโครงร่างแต่ละหมวด

เอกสารข้อกำหนดความต้องการซอฟต์แวร์ (SRS) แบบกระชับสำหรับทีม Agile

เอกสาร SRS ไม่ใช่การเขียนนิยาย 100 หน้า แต่คือ "สัญญาความเข้าใจร่วมกัน" ระหว่างทีมพัฒนากับอาจารย์/เจ้าของร้าน ก่อนลงมือเขียนโค้ด

วัตถุประสงค์: พัฒนาระบบ Grocery POS สำหรับร้านค้าปลีกขนาดกลาง รองรับแคชเชียร์ 2–3 จุดพร้อมกัน

ขอบเขตที่ทำ (In-Scope): ขายหน้าร้าน, รับชำระ PromptPay/เงินสด, ตัดสต็อก, แจ้งเตือนสินค้าใกล้หมด และรายงานยอดขาย
ขอบเขตที่ยังไม่ทำในเฟสนี้ (Out-of-Scope): ระบบบัญชีภาษีเต็มรูปแบบ และแอปสั่งซื้อออนไลน์สำหรับลูกค้า

กลุ่มผู้ใช้ (User Classes): Cashier (ใช้งานทุกวัน เน้นความเร็ว), Manager (ดูรายงาน/อนุมัติ Void), Admin (จัดการผู้ใช้)

ข้อจำกัดทางเทคนิค: ใช้ฐานข้อมูลเชิงสัมพันธ์ MySQL/PostgreSQL (3NF), รองรับเครื่องอ่านบาร์โค้ด USB HID และเครื่องพิมพ์ใบเสร็จความร้อน 80mm

Use Cases หลัก: UC-01 Check Out Item (สแกนบาร์โค้ด → แสดงราคา → ชำระเงิน → พิมพ์ใบเสร็จ), UC-02 Manual Price/Barcode Fallback (กรณีบาร์โค้ดอ่านไม่ออก)

Data & Traceability: ทุก FR ต้องผูกกับรหัส User Story (US-xxx) และ Test Case (TC-xxx) เพื่อยืนยันความครบถ้วน

07 · ACCEPTANCE CRITERIA DEFINITION OF DONE · GIVEN-WHEN-THEN FORMAT

เกณฑ์การให้คะแนนและรายการส่งมอบงานของทีม (Week 3 Workshop)

ตรวจสอบความครบถ้วนของเอกสาร SRS, Backlog และ Risk Register เทียบกับเกณฑ์ประเมินระดับ "ดีเยี่ยม (22–25 คะแนน)"

ระดับคุณภาพ ช่วงคะแนน ลักษณะงานตามเกณฑ์รายวิชา 1145 204
ดีเยี่ยม 22–25 วิเคราะห์ FR/NFR ได้ถูกต้อง ครอบคลุม เขียน User Stories ตามมาตรฐาน Agile พร้อมประเมิน Story Points และระบุ Acceptance Criteria ได้อย่างสมบูรณ์
ดี 18–21 Requirements และ User Stories ครอบคลุมฟังก์ชันหลักของระบบ มีการประเมิน Story Points โดยมีจุดที่ต้องปรับแก้เล็กน้อย
พอใช้ 14–17 User Stories เขียนไม่ถูกรูปแบบ ขาดรายละเอียด Acceptance Criteria หรือวิเคราะห์ Requirements ไม่ครอบคลุม
