04 · COLLABORATIVE WORKFLOW

โครงสร้างคอลัมน์มาตรฐานบน GitHub Projects

  • Product Backlog & Sprint Backlog — เก็บ User Stories ก่อนแตกเป็น Issue ย่อย
  • Todo → In Progress — งานย่อยระดับ Task ที่จบได้ภายใน 4–16 ชม. (ไม่เกิน 1 วัน)
  • Awaiting Review — เปิด Pull Request (PR) และให้เพื่อนร่วมทีม/ที่ปรึกษาตรวจ Code Review
  • Icebox — แช่แข็ง User Stories ที่ยังไม่อยู่ในขอบเขต Sprint 2 เพื่อป้องกัน Scope Creep

Git Branching & Commit Standard (เกณฑ์ประเมิน Sprint 2)

  • Branch แยกตามฟีเจอร์: main (พร้อมเดโม) ← develop ← feat/ml-reorder, fix/stock-lock
  • เกณฑ์ระดับดีเยี่ยม (22–25 คะแนน): ประวัติ Git commit ใน Sprint 2 มีความต่อเนื่อง สมาชิก (1–3 คน) มีส่วนร่วมพัฒนาฟีเจอร์ระดับสูงอย่างสมดุล
  • ความเสี่ยงที่ต้องเลี่ยง: การรวมโค้ดก้อนใหญ่คืนเดียวก่อนสอบ (Big-bang commit) ทำให้ตรวจสอบย้อนกลับไม่ได้

07 · ADVANCED FEATURE 02 · CLOUD & CONCURRENCY

กลไก Cloud Sync และการป้องกันสต็อกติดลบเมื่อขายพร้อมกัน

CLO2 CLO3 ACID & Outbox Pattern

จำลองเหตุการณ์ Race Condition & Sync

สถานการณ์: เหลือ น้ำดื่มแพ็ค 12 ขวด ในคลังเพียง 1 แพ็คสุดท้าย แต่เครื่องแคชเชียร์ A และ B กดคิดเงินพร้อมกัน

หลักการออกแบบ Cloud Sync สำหรับร้านค้า 1. ใช้ Idempotency-Key (UUID ต่อบิล) ป้องกันการตัดสต็อกซ้ำเมื่อเครือข่ายส่ง Retry
2. ใช้ Outbox Queue เก็บบิลลง Local Storage/SQLite ของเครื่องขายเมื่อเน็ตหลุด แล้วค่อย Sync ตามลำดับเวลา
เครื่องแคชเชียร์ A (Online) พร้อมทำงาน

ส่งคำสั่งซื้อ: น้ำดื่ม 1 แพ็ค (t = 0.00s)

เครื่องแคชเชียร์ B (Sync / Concurrent) พร้อมทำงาน

ส่งคำสั่งซื้อ: น้ำดื่ม 1 แพ็ค (t = 0.02s)

  • Quality & Automation: เขียน Unit Test / Integration Test, ทำ Code Review ผ่าน PR และตั้งค่า CI Pipeline
