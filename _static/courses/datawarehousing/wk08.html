Part 1: Foundations

“Why physical design?”

Logical บอกว่าเก็บอะไร — Physical บอกว่าเก็บอย่างไรให้เร็วและถูก

  • • Star schema ที่ไม่มี index ต้อง full scan ทุกครั้ง → ช้า
  • • DW อ่านมาก เขียนน้อย → ปรับจูนเพื่อ read performance ได้เต็มที่

Logical vs Physical Design

Logical Design

  • • Star schema, snowflake, grain
  • • Fact + Dimension (เช่น fact_sales, dim_product)
  • • ไม่ผูกกับ DBMS ใด

Physical Design

  • • Storage, pages/blocks, tablespace
  • • Indexes, Partitioning, Tuning
  • • ผูกกับ PostgreSQL / Snowflake / BigQuery
ตัวอย่าง: Logical บอก fact_sales(date_key, product_key, amount) — Physical เลือก partition by date_key + index on product_key

Storage: Row vs Columnar

Row Store (Postgres heap)

เก็บทั้งแถวใน 8KB page — ดีกับ OLTP (อ่าน/เขียนทีละแถว)

Heap + TOAST สำหรับค่าขนาดใหญ่

Columnar (DW)

ClickHouse, Snowflake micro-partitions, BigQuery Capacitor — อ่านเฉพาะคอลัมน์ที่ SELECT, บีบอัดสูง

เหมาะกับ OLAP: SELECT SUM(amount) WHERE year=2024 ข้ามคอลัมน์อื่นทั้งหมด

Takeaway: บน PostgreSQL ที่เป็น row store เราจึงต้องพึ่ง index + partitioning มาก — ส่วน Snowflake/BigQuery ใช้ clustering / partitioning แทน index แบบดั้งเดิม

Part 2: Indexing

“Catalog ของห้องสมุด”

Index คือโครงสร้างช่วยค้นหาโดยไม่ต้องสแกนทั้งตาราง — แลกมาด้วยพื้นที่และเวลาตอนเขียน

โฟกัส: B-Tree • Bitmap • BRIN • Composite • Covering • Star-join indexing

B-Tree Index — จุดเริ่มต้น

How it works

ต้นไม้สมดุล B-Tree — ค้นหา =, <, >, BETWEEN, ORDER BY ใน O(log n)

CREATE INDEX idx_fact_sales_date
  ON fact_sales(date_key);
-- หรือ B-Tree เป็น default
CREATE INDEX idx ON fact_sales
  USING btree (date_key);

Postgres index types →

When to use in DW

  • • FK ของ fact: product_key, customer_key
  • • high-cardinality (เช่น 500 customers)
  • • ใช้กับ JOIN + EXPLAIN จะเห็น Index Scan
EXPLAIN ANALYZE
SELECT * FROM fact_sales
WHERE date_key = 523;
-- Seq Scan -> Index Scan หลังสร้าง index

Beyond B-Tree

Bitmap

บิตเวกเตอร์ต่อค่าต่าง → ดีกับ low-cardinality (tier, region)

-- Postgres จำลองด้วย B-Tree + bitmap scan
-- Oracle มี native bitmap
SELECT * FROM dim_customer
WHERE tier='Gold'; -- BitmapAnd/Or

Bitmap index →

BRIN

Block Range Index — สรุป min/max ต่อ block range, เล็กมาก

CREATE INDEX idx_brin
 ON fact_sales USING BRIN(date_key)
 WITH (pages_per_range=128);

ดีกับ append-only fact เรียงตามเวลา

Hash & อื่นๆ

Hash เฉพาะ = — ไม่เรียงลำดับ, น้อยครั้งใน DW

CREATE INDEX idx_hash
 ON dim_customer USING hash(email);

GIN สำหรับ JSON/FTS

DW เลือก: Fact FK = B-Tree หรือ BRIN, Dimension low-card = bitmap scan อัตโนมัติ

Composite & Covering Index

Composite (หลายคอลัมน์)

ลำดับสำคัญ: คอลัมน์กรองบ่อยก่อน

CREATE INDEX idx_fact_cover
 ON fact_sales(date_key, product_key);
-- ใช้ได้กับ WHERE date_key=... AND product_key=...
-- หรือ WHERE date_key=... (leftmost prefix)

Multicolumn indexes →

Covering + INCLUDE

Index-only scan — ไม่ต้องแตะ heap

CREATE INDEX idx_cover
 ON fact_sales(date_key, product_key)
 INCLUDE (amount, quantity);
-- SELECT amount WHERE date_key=... อ่านแค่ index

Index-only scans →

Star-join tip: บน fact_sales สร้าง composite บน (date_key, product_key, customer_key) ตาม query pattern ยอดนิยมของคุณ — วัดด้วย pg_stat_statements

Rule of thumb
  • Fact FK ทุกตัว → index (เว้นแต่จะ partition นั้นอยู่แล้ว)
  • Dimension PK → primary key (B-Tree)
  • Where-filter บ่อย → composite / covering
DW-specific
  • Bitmap scan อัตโนมัติเมื่อ filter หลาย FK
  • Columnar: ไม่ต้อง index — ใช้ clustering / clustering

อ้างอิง: Kimball Star Schema • Use The Index, Luke!

EXPLAIN ANALYZE ก่อน/หลัง Index

Before (Seq Scan)

EXPLAIN ANALYZE
SELECT SUM(amount) FROM fact_sales
WHERE date_key BETWEEN 400 AND 430;
-- Seq Scan on fact_sales
--   Filter: (date_key >=400 AND <=430)
--   Rows: 2134  Time: 18.4 ms

ต้องอ่านทุก page

After (Index Scan + Pruning)

CREATE INDEX idx_fact_sales_date
  ON fact_sales(date_key);
ANALYZE fact_sales;
EXPLAIN ANALYZE
SELECT SUM(amount) FROM fact_sales
WHERE date_key BETWEEN 400 AND 430;
-- Index Scan using idx_fact_sales_date
--   Buffers: shared hit=45
--   Time: 1.2 ms (15x faster)

EXPLAIN docs →

-- Copy-paste: วัดขนาด index
SELECT relname, pg_size_pretty(pg_relation_size(indexrelid)) FROM pg_stat_user_indexes WHERE relname LIKE 'idx_fact%';

Part 3: Partitioning

“Divide and conquer”

Partitioning แบ่งตารางใหญ่เป็นชิ้นเล็ก — query อ่านเฉพาะชิ้นที่เกี่ยวข้อง (partition pruning)

ประเภท: Range • List • Hash — และใช้ร่วมกับ index ได้

Why Partition?

⚡

Pruning

WHERE date_key BETWEEN 400-430 → scan 1 จาก 8 partitions

Partition pruning →

🧹

Maintenance

DETACH old partition แทน DELETE ล้านแถว

📦

Manageability

VACUUM / REINDEX ทีละ partition — ลด lock

เมื่อไหร่ควร partition? Fact > 10M แถว, filter ตามเวลา/ภูมิภาค บ่อย, ต้องลบ/archiving เป็นช่วง — ไม่ใช่ทุกตารางต้อง partition! Postgres Partitioning docs →

Types of Partitioning

Range

ตามช่วงต่อเนื่อง — เช่น date_key, order_date

PARTITION BY RANGE (date_key)
FOR VALUES FROM (1) TO (91) -- Q1

List

ตามค่าที่ระบุ — เช่น region

PARTITION BY LIST (region)
FOR VALUES IN ('North','South')

Hash

กระจายสม่ำเสมอ — เช่น customer_key

PARTITION BY HASH (customer_key)
PARTITIONS 4

Cloud: Snowflake clustering • BigQuery partitioned tables • ClickHouse partitioning

Demo: Declarative Partitioning

Copy-paste (PostgreSQL 15+):

CREATE TABLE fact_sales_part (
  sale_id INT NOT NULL,
  date_key INT NOT NULL,
  product_key INT NOT NULL,
  customer_key INT NOT NULL,
  quantity INT NOT NULL,
  amount NUMERIC(12,2) NOT NULL,
  PRIMARY KEY (sale_id, date_key)
) PARTITION BY RANGE (date_key);

-- 8 quarterly partitions (731 days ~ 8 quarters)
CREATE TABLE fact_sales_part_q1 PARTITION OF fact_sales_part
  FOR VALUES FROM (1) TO (92);
CREATE TABLE fact_sales_part_q2 PARTITION OF fact_sales_part
  FOR VALUES FROM (92) TO (183);
-- ... q3 .. q8

INSERT INTO fact_sales_part SELECT * FROM fact_sales;

-- Verify pruning
EXPLAIN SELECT SUM(amount) FROM fact_sales_part
WHERE date_key BETWEEN 400 AND 430;
-- Append -> Seq Scan on fact_sales_part_q5 only

Maintenance & Gotchas

Do ✅

  • • Partition key ควรรวมใน PK / unique constraint
  • • สร้าง index แยกต่อ partition (local index)
  • • Archiving: DETACH PARTITION แทน DELETE
ALTER TABLE fact_sales_part
  DETACH PARTITION fact_sales_part_q1;
-- เร็วกว่า DELETE WHERE date_key <92

Avoid ❌

  • • Partition เล็กเกิน (หลายพัน partitions → planner ช้า)
  • • เลือกคอลัมน์ที่ไม่ถูก filter บ่อย
  • • ลืม ANALYZE หลัง load
-- Check partition sizes
SELECT relname,
 pg_size_pretty(pg_relation_size(relid))
FROM pg_partition_tree('fact_sales_part');

Week 8 Summary

1. Physical design = performance — Indexes ช่วยค้นหา, Partitioning ช่วยตัดข้อมูลที่ไม่เกี่ยว
2. Index เลือกให้ถูก: B-Tree สำหรับ FK, BRIN สำหรับ fact เรียงเวลา, Covering สำหรับ index-only scan
3. Partition แบบ Range ตามเวลาเป็นมาตรฐาน DW — ใช้ pruning ให้เป็นประโยชน์
4. วัดจริงด้วย EXPLAIN ANALYZE — อย่าเดา, ให้ข้อมูลบอก
